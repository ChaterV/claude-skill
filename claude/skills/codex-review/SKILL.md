# Codex 审查（用户主动触发）

`SK=${CLAUDE_SKILL_DIR}`：本 skill 所在目录，下文命令中的 `$SK` 都替换成这个绝对路径。如果这里显示的不是绝对路径（旧版 Claude Code 不替换该变量），改用加载时提示的 Base directory。

## 1. 判断审查对象

**用户提到"计划""方案"时 → 计划审查**，用 `--plan <计划文件>`：
- "这个计划"指对话里最近写的或讨论的计划文件。拿不准是哪个文件，或者计划只在对话里、还没写成文件时，先问用户（或征得同意后写到项目目录）。
- 计划审查只审计划本身，不看工作区里的其他改动。

**否则 → 代码审查**：

| 用户的说法 | 参数 |
|---|---|
| 没说范围 | 不传，脚本自动判断：工作区有改动 → 未提交改动；否则 → 当前分支相对默认分支 |
| "未提交的""工作区的" | `--uncommitted` |
| "这个分支""相对 master" | `--base <分支>` |
| "这个提交""上一个提交" | `--commit <sha>`（"上一个提交"用 `HEAD`） |

**两种审查通用**：
- 用户提到关注点（如"重点看性能""看看有没有安全问题"）时，加 `--focus "<关注点>"`。可以把对话里相关的需求要点、用户决策一并写进去，让 Codex 能对照意图审查。没有关注点就不传。
- 用户点名模型时才加 `--model`。
- 如果 `codex-delegate` 的 Codex 正在同一目录写文件，等它结束后再审查。

## 2. 运行（Bash，`run_in_background: true`）

```bash
$SK/scripts/review.sh "<scratchpad>/codex-reviews/<短名>-<HHMM>" --cd <仓库目录> [审查对象参数] [--focus "..."]
```

告诉用户审查已在后台开始（通常需要一到几分钟），然后结束本轮回复，等待完成通知。不要轮询。

## 3. 核实并汇报

完成通知里已包含完整的审查意见，不需要再读文件。

1. **逐条核实**：用 Read 读每条意见引用的代码行（前后各留约 10 行）；计划审查还要对照计划里对应的步骤。**所有意见要读的代码在同一次请求里并行读**，不要一条一条地读。如果结论取决于引用范围以外的代码（调用方、被调函数、配置），可以追读一到两处，只读相关的函数，不要通读文件；需要追读的也集中在下一次请求里并行读。判断该意见是否成立：
   - **确认**：问题确实存在；
   - **存疑**：取决于上下文或运行时条件，或者现有证据不足以判断；
   - **误报**：必须能指出代码里已经处理了该问题的具体位置，或者 Codex 依据的事实是错的（比如引用的代码不存在、读错了逻辑）。**找不到这样的证据，最多标「存疑」，不能标「误报」。**

   每条给一句理由，并写明依据的代码位置（`文件:行号`）。不要通读整个 diff 或整个计划，不要扩大审查范围。意见超过 8 条时，只核实 P0/P1，其余标「未核实」。
2. **用中文汇报**：按优先级从高到低排列，每条包括：优先级、标题、位置（`文件:行号`，计划审查再加上计划中的步骤）、Codex 的说明（简述）、Claude 的核实结论、理由和依据位置。没有意见时，直接说明 Codex 未发现问题。
3. **停下**：不要修改代码或计划，问用户采纳哪些。

## 4. 用户选定要采纳的意见后

- **计划审查**：Claude 按采纳的意见修改计划文件，并在汇报里列出改了哪些地方。之后用户可以要求复审，或交给 `codex-delegate` 执行。
- **代码审查**：改动小（几行、意思明确）的 Claude 直接改；改动大或涉及多个文件的，用 `codex-delegate` 委托，把选中的意见整理成执行计划。
- 用户要求复审时，用同样的参数再跑一次。

## 出错时

通知里会附上错误事件和 stderr 末尾。常见原因：
- 未登录：让用户运行 `! codex login`；
- 范围内没有改动：换一个范围；
- 分支名、提交号或计划路径写错：核对后重试。
