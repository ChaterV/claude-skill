# Codex 委托：Claude 决策，Codex 执行

Claude 负责调研、写计划、回答决策问题、验收；Codex 负责按计划改代码、跑命令和测试、自行修复执行中的失败，不改计划、不做计划外改动。

**token 原则**：Codex 执行期间，Claude 只在一轮结束、出现阻塞或异常时被唤醒（后台模式下还包括需要决策时；窗格和 tab 模式的决策由用户直接在 Codex 界面里做）。机械性工作全部交给 Codex。Codex 停下却没交结果时，后台和窗格模式的脚本会自动催它继续，不唤醒 Claude；tab 模式由用户在 tab 里让它继续。

`SK=${CLAUDE_SKILL_DIR}`：本 skill 所在目录，下文和 references 文档中的 `$SK` 都替换成这个绝对路径。如果这里显示的不是绝对路径（旧版 Claude Code 不替换该变量），改用加载时提示的 Base directory。

## 1. 调研与计划（Claude 自己做）

- 调研到能写出**具体执行计划**为止：每一步都落到文件、位置和改法，让 Codex 不需要再做方案判断。
- 涉及用户决策的问题，委托之前先问清楚，不要留给 Codex 猜。
- 从讨论中提炼**验收清单**（目标、用户的决策、预期行为、不做的事），写进简报的「验收标准」。每一条标明证据类型，这决定了验收时能不能少读 diff：
  - 【命令】能用命令判定的：测试、类型检查、构建、`rg` 计数（例如旧写法计数应为 0、新写法计数应为 N）。**尽量把条目改写成这一类**，批量机械改动尤其要写出检查不变量的命令。
  - 【读码】只能读代码判定的：语义和分支逻辑、是否采用了用户选定的方案。
- 调研时记下**代表性文件**（结构特殊、处理边界情况、最容易改错的），验收时优先抽查它们。
- 计划里写上 Codex 要跑的验证命令，并确认命令本身能跑（例如 Node 24 中 `node --test <目录>` 会报错，要写成具体文件或 glob）。

## 2. 写简报

- 先确定模式（见第 3 步），然后在**同一次请求里并行读** `$SK/references/brief-template.md` 和对应模式的文档，不要分两次读。
- `RUN=<scratchpad>/codex-runs/<短任务名>-<HHMM>`，按模板写 `$RUN/brief.md`。
- Codex 看不到这段对话，也读不到 CLAUDE.md 和 memory，只会自动读仓库里的 AGENTS.md。调研结论、用户的决策和相关偏好都写进「关键上下文」。
- **只写文件路径、行号和符号名，让 Codex 自己读，不要粘贴代码。** 不要重复 AGENTS.md 里已有的规则。

## 3. 权限与启动

| 场景 | 参数 |
|---|---|
| 改代码（默认） | `--sandbox workspace-write`（可写工作目录，不能联网） |
| 只读任务 | `--sandbox read-only`，只能用后台模式（窗格和 tab 模式下 Codex 写不了结果文件） |
| 需要装依赖、请求接口 | 再加 `--network` |
| 不受沙箱限制 | `--sandbox danger-full-access`，必须先征得用户同意 |

同一工作目录里不要同时跑两个会写文件的 Codex 任务；Codex 运行期间，Claude 不要改它负责的文件。

模式只读对应的那一份文档并照做（第 2 步已和模板一起读过）：
原则：**只要委托了 Codex，就让用户看到它**。
- `HERDR_ENV=1` → 窗格模式（分屏）：`$SK/references/pane.md`
- 不在 herdr 中 → tab 模式（当前终端新开 tab，开不了就用 macOS 自带终端开新窗口）：`$SK/references/tab.md`
- 只读任务、用户要求后台运行，或 `tab.sh open` 返回 5（开不了可见窗口，例如 SSH）→ 后台模式：`$SK/references/background.md`。最后这种情况要告诉用户这次看不到 Codex 的界面

始终通过脚本调用 Codex，不要绕过脚本直接执行 `codex exec`。

## 4. 处理结果

完成通知里已带有结果摘要（状态、步骤、改动文件、验证结果、问题和假设），通常不需要再读结果文件。按 `status` 处理：

- **completed** → 第 5 步验收。
- **needs_input**（仅后台模式；窗格和 tab 模式下 Codex 直接问用户，不会交回这个状态）→ Claude 自己判断：计划层面的问题（计划不可行、有更好的做法、需改计划外文件）根据调研结论决定；只有涉及用户意图、业务取舍或高风险操作时，才用 AskUserQuestion 问用户（选项来自 `options`，Codex 推荐的放第一个并标「(推荐)」）。然后写 reply，进入第 6 步。
- **blocked** → 多半是沙箱、网络或凭据问题，跟用户确认后调整权限。
- **failed / 没有结构化结果** → 看摘要附带的原文，判断是发指令修正，还是调整计划后重新委托。

## 5. 验收（分级）

原则：以实际代码和 Claude 亲自跑出的结果为证据，不以 Codex 的自述为证据。`steps=done`、`verification=passed` 只说明 Codex 认为自己做完了。不审查 Codex 写的测试脚本。验收力度按**风险**定，不按改动规模定：规模大但机械的改动，靠命令覆盖全部文件，靠抽查确认理解没错，不逐个文件读。

**默认：分层验收**
1. **范围**：`git diff --stat`，改动文件是否都在计划范围内，有没有计划外文件。
2. **【命令】条目**：Claude 自己重跑，覆盖全部文件。输出只看结论（如 `| tail -n 20`、`rg -c`），不要把长输出读进上下文。
3. **【读码】条目**：每条都读对应的 diff 片段（`git diff -U2 -- <file>`），不因规模大而省略。重点查两件事：是否采用了用户选定的方案（有没有悄悄换成被否掉的方案）；是否改变了不允许改变的现有行为。
4. **抽查**：在其余改动文件中挑 2–3 个读 diff。挑法：先挑第 1 步记下的代表性文件，再挑改动行数最多的；不要随便挑。
5. 摘要里标为 `deviated` / `skipped` 的步骤，读对应的 diff，判断理由是否成立。

**升级为完整验收**（逐个文件读 diff，逐条核对清单，并在代码里走一遍关键输入或实际运行一个关键场景）：
- 用户要求完整验收；
- 涉及接口字段、金额/价格计算、权限、数据删除等高风险逻辑；
- 第 1–5 步发现了任何偏差：抽查出错，说明 Codex 可能对计划的理解整体有误，其余文件也不能信；
- 验收标准里没有【命令】条目，而改动又不止几个文件（没法用命令覆盖全部文件）。

**处理不一致**：在 reply 里写清楚哪一条、现在是什么样、期望是什么样，让 Codex 再做一轮，修完后只复查这几条。一两行的小偏差 Claude 直接改。如果是计划或理解有误，先和用户确认。

**向用户汇报**：逐条列出核对结论（符合 / 已修正 / 有偏差及原因），注明这次是分层还是完整验收、跑了哪些命令、抽查了哪几个文件，再列出 Codex 的假设和遗留问题。不要复述执行过程。

## 6. 后续轮次

写 `$RUN/reply-<n>.md`：按 question id 逐条给出决定，或写修订/追加的步骤（写法同简报的「执行计划」）。然后按所在模式的文档发起下一轮。后续的修复和追加任务优先沿用同一个会话，不用重写完整简报。

## 7. 停止与收尾

- 用户中途叫停：按所在模式文档的「停止」一节处理。已经产生的改动留在工作区，用 `git status --short` 看一下并告诉用户。
- Codex 不负责提交代码。需要 commit 时，由 Claude 按用户的规则处理。
